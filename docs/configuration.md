# Configuration

agentcheckup works without configuration. To change targets or rule severities, add
`agentcheckup.config.json` to the directory you scan.

```json
{
  "$schema": "https://raw.githubusercontent.com/mustafakbaser/agentcheckup/main/schemas/config.schema.json",
  "targets": ["claude-code", "codex", "cursor"],
  "rules": {
    "instr/claude-md-too-long": ["warn", { "maxLines": 300 }],
    "skill/non-portable-field": "off"
  },
  "ignore": ["test/fixtures/**"],
  "overrides": [
    {
      "files": ["examples/**"],
      "rules": { "skill/description-quality": "off" }
    }
  ]
}
```

The configuration is JSON on purpose. agentcheckup never executes code from the repository it
scans, so JavaScript or TypeScript configuration files are not supported.

## Fields

| Field       | Type         | Meaning                                                                                                                                                                                                                                                                                   |
| ----------- | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `targets`   | platform ids | Agents to check against. Rules about other agents are skipped, and `context` plans only their agents. Default: all of `claude-code`, `codex`, `cursor`, `copilot` (its CLI, VS Code and cloud agent), `gemini`, `windsurf` (Devin Desktop), `cline`. The `--targets` flag overrides this. |
| `rules`     | object       | Per rule: `"off"`, `"info"`, `"warn"`, `"error"`, or `[severity, options]`.                                                                                                                                                                                                               |
| `ignore`    | globs        | Files to skip, relative to the scanned directory. Files ignored by `.gitignore` are skipped already. Load plans and the matrix leave them out too, and each plan counts them.                                                                                                             |
| `overrides` | array        | Change rule severities for files matching `files`. Later overrides win. Options can only be set in the top-level `rules`.                                                                                                                                                                 |

Globs use [picomatch](https://github.com/micromatch/picomatch) syntax and match dotfiles.

Unknown rule ids in the configuration produce a warning: a `!` line in the report of a
`stylish` or `markdown` scan, `Warning:` on stderr otherwise. Unknown fields are an error, so a
typo cannot silently disable a check.

Rule options are checked before any rule runs. An option the rule does not take, or a value of
the wrong type, exits with code 2 and names the rule, the option and the type it needs:

```text
Invalid agentcheckup.config.json:
  - rules["instr/claude-md-too-long"].maxLines: expected a positive integer, got "many".
```

The options of a rule are on its page in the [rule catalog](rules/README.md), and
[`schemas/config.schema.json`](../schemas/config.schema.json) describes them for editors. When
the configuration has an error, the message lists its unknown rule ids too. `scan()` in the
[API](api.md) throws a `ConfigError` for the same configurations.

## Inline suppressions

Suppress one finding on the next line, with a reason:

```markdown
<!-- agentcheckup-disable-next-line instr/import-unresolved -- generated by our docs build -->

@docs/generated/api.md
```

Suppress rules for a whole file:

```markdown
<!-- agentcheckup-disable-file skill/body-too-long -- reference skill, loaded on demand -->
```

Inside YAML frontmatter, use a YAML comment:

```yaml
---
name: deploy
# agentcheckup-disable-next-line skill/non-portable-field -- Claude Code only
when_to_use: Before every production deploy
---
```

Rules:

- The reason after `--` is required. A directive without one is reported and has no effect.
- A directive that no longer suppresses anything is reported, so stale suppressions do not
  accumulate.
- A suppressed finding does not count toward the exit code or the score. `stylish` output hides
  it unless you pass `--show-suppressed`; `json` keeps it with a `suppressed` field, `sarif` marks
  it as suppressed, and `markdown` and `github` leave it out.
- JSON files cannot hold comments, and directives in TOML comments are not read. Use `overrides`
  for both.
- A directive applies to findings in its own file. That includes a file an instruction file
  imports, such as a `README.md` that `CLAUDE.md` imports with `@README.md`.
- `--untrusted` ignores all inline directives. See
  [Scanning untrusted repositories](#scanning-untrusted-repositories).

## Scanning untrusted repositories

Use `--untrusted` for pull requests from forks and other third-party code. It ignores the
repository's configuration file and all inline directives, so the code under review cannot turn
checks off.

It also does not let the repository's `.gitignore` hide agent configuration. Agents load
committed files whether or not `.gitignore` names them, so a change could otherwise commit a
`.mcp.json` with `git add -f`, list it in `.gitignore` and keep it out of the scan. With
`--untrusted`, every directory is listed even where `.gitignore` excludes it, and agent files
such as `CLAUDE.md`, `.mcp.json` and `packages/x/.claude/settings.json` are read wherever they
are. Other ignored files stay unread.

It also scans the build output and vendored directories a trusted scan leaves out: `vendor`,
`dist`, `build`, `out`, `target` and `coverage`. A repository can commit agent configuration
there, and agents load it: a session started in `vendor/x` reads its `.claude/settings.json`
and `.mcp.json`. Run an untrusted scan on a fresh checkout, where these directories hold only
committed files; in a working copy with large build output, the scan can reach its limit of
200,000 directory entries.

### What no scan reads

- Dependency, cache and version control directories: `node_modules`, `bower_components`,
  `.pnpm-store`, `.yarn`, `.venv`, `venv`, `__pycache__`, `.cache`, `.next`, `.nuxt`, `.turbo`,
  `.mcpb-cache`, `.git`, `.hg`, `.svn` and `.claude/worktrees`, outside agent configuration
  directories. Package managers and tools write them; an agent configuration file committed
  there is not checked.
- Files that instruction files import, where `.gitignore` excludes them. If `.gitignore` excludes
  `docs/`, the scan does not read `docs/guide.md` for a `CLAUDE.md` that imports
  `@docs/guide.md`. Add `--no-gitignore` to read them.

### What a scan could not check is reported

A scan never reads as clean when it could not see something. Every format says so: stylish and
Markdown output with a note, GitHub output with a warning or notice annotation, SARIF with a
tool notification, JSON in `skipped`, `unscannedConfig` and `inventory.incomplete`, and the
`context` and `tokens` views with a note under the plans. `--gate` and `--policy` treat it as not
analyzed and fail closed ([Baselines and the gate](context.md#what-the-scan-could-not-analyze)):

- **Limits.** Files over 4 MiB (the largest file an agent documents loading in full), files past
  the 64 MiB the scan reads in all, binary and unreadable files, directories deeper than 32
  levels, and everything after the first 200,000 directory entries.
- **Left out on purpose.** Without `--untrusted`, agent configuration that `.gitignore` excludes
  or that lies in a build output or vendored directory is counted, not read: "2 agent
  configuration files are excluded by .gitignore; add --no-gitignore to check them". The count
  lists at most 20,000 directory entries.

## Organization policy

`--policy <file>` checks a scan against rules your organization sets: which MCP servers may run,
forbidden settings, denied tools and commands, required hooks and startup budgets. It implies
`--untrusted`, so the repository cannot switch a check off, and it cannot be combined with
`--config`. A violation fails the run with exit code 1 unless the policy is in audit mode; a
policy file that is not valid exits with code 2. [Organization policy](policy.md) describes the
format, the checks and the trust model.

## How much a scan shows

The `stylish`, `markdown` and `github` formats have three levels of detail. In `stylish`:

| Level   | Flag        | What it shows                                                                                                                                                                                                                                                                                                                 |
| ------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| compact | `--compact` | The findings and the totals, without what each agent misses and without `why`, `fix` and `how` lines. A finding with a fix ends with `fixable` (a safe fix) or `fixable (review)`.                                                                                                                                            |
| default | none        | First, what each agent misses: the skips in the load plans of each agent at the root, each with the class of its fix or `manual`. Under each finding, a `why` line when the plans add a fact the message lacks, then a `fix` line (class and title) or a `how` line (a manual step). Last, the number of fixes of each class. |
| verbose | `--verbose` | The default, plus each rule's docs URL, the first paragraph of its rationale and its sources.                                                                                                                                                                                                                                 |

In `markdown`, the default level adds a table of what each agent misses, a Fix column and a line
on how to preview the fixes. In `github`, it adds `Why`, `Fix` or `How`, and `Docs` lines to each
annotation, whose title names the fix class at every level. `--compact` leaves these additions
out, and `--verbose` shows the same as the default in both formats.

`--compact` and `--verbose` cannot be combined, and they do not change `json`, `sarif` or
`badge`. [Fixing findings](fix.md) explains the fix classes.

## What each agent loads

`agentcheckup context [path]` shows the load plan of each of nine agents, with Copilot's CLI, VS
Code and cloud agent planned separately: what is in context when a session starts, what loads
on demand, the MCP servers and hooks it starts, and what it skips and why. A skip that `agentcheckup fix` can remove ends with `fix: safe`, `fix: review`, or
`needs your words (fix -i)`. It never fails on findings. [What each agent loads](context.md)
explains the output.

| Option                 | Meaning                                                                                                                                                                                                                                                                |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--agent <list>`       | Agents, comma-separated: `claude-code`, `codex`, `cursor`, `copilot-cli`, `copilot-vscode`, `copilot-cloud`, `gemini`, `windsurf` (Devin Local), `cline`. `copilot` stands for its three surfaces, `all` for every agent. Default: those among the configured targets. |
| `--cwd <dir>`          | Plan a session started in this directory, relative to the scanned path. No `..`; the directory must exist. Default: the root.                                                                                                                                          |
| `--matrix`             | Also plan Codex in each directory with an `AGENTS.md`, and show which agent reads which file. Cannot be combined with `--cwd`.                                                                                                                                         |
| `--context-window <n>` | The model's context window in tokens, for limits that depend on it, such as the skills listing.                                                                                                                                                                        |
| `--format <name>`      | `text` (default), `json` or `markdown`. JSON is the same report a scan writes.                                                                                                                                                                                         |

The command also takes `--output`, `--baseline`, `--gate`, `--config`, `--no-config`,
`--untrusted` and `--no-gitignore`, with the same meaning as for a scan. Rule options feed the
plans: the `maxBytes` option of `instr/codex-size-budget` sets the Codex byte limit the plan
assumes, unless a `.codex/config.toml` on the path sets `project_doc_max_bytes`, which wins.
Files that `ignore` matches are left out of the plans and the matrix; each plan says how
many it left out, because agents still load them
([Files the configuration ignores](context.md#files-the-configuration-ignores)). `--untrusted`
does not read the configuration, so it shows them.

On a regular scan, `--context` adds the plans and the matrix that `context --matrix` makes
(every agent at the root, plus Codex in each directory with an `AGENTS.md`) to the report, and
`--context-window` needs it. Use `--context` for the scan that writes a baseline, so a later
comparison also shows how session-start context changed. How findings, inventory items and plan
entries are matched, and exactly when each gate class trips, is in
[Baselines and the gate](context.md#baselines-and-the-gate).

## Baselines and the gate

`--baseline <report.json>` compares a scan with the JSON report of an earlier one, usually the
base branch of a pull request:

```sh
agentcheckup --context --format json --output base.json --fail-on none   # on the base
agentcheckup --baseline base.json --gate security                         # on the change
```

- Findings match by fingerprint and are marked `new` or `unchanged`. `--fail-on` counts new
  findings only; the score still covers every finding. Fingerprints survive lines inserted
  above, re-indentation, trailing commas and reordered JSON keys.
- `--gate` names the changes that fail the run: the security-relevant classes `mcp`,
  `mcp-unpinned`, `permissions`, `hooks`, `env` and `unicode`, `models` for agent definitions
  and model settings, `security` for every class but `models`, or `none`. Removals trip it
  only for a `deny` or `ask` permission entry (`permissions`) and a model setting (`models`).
  `--gate` without `--baseline` is a usage error.
- `permissions` trips on every entry that lets an agent do more without asking: any
  `permissions.allow` entry, narrow ones such as `Bash(curl:*)` included, extra directories, a
  skill's `allowed-tools`, MCP auto-approval, Gemini CLI `trust`, a new `defaultMode`, and
  Codex settings such as `approval_policy = "never"`. The
  summary marks broad entries, such as `Bash (broad: runs any shell command)`. A removed
  `deny` or `ask` entry trips it; an added one never does.
  [Gate classes](context.md#gate-classes) has every class.
- `--context` on the base scan adds the load plans, so the comparison also shows the change in
  session-start context per agent.
- The baseline is read as untrusted input: at most 64 MiB, a regular file (not a symlink), and
  only a report with a supported `schemaVersion` and the same `fingerprintVersion`. Anything
  else exits with code 2: a baseline written before fingerprint version 3, which changed how
  inventory items are digested, must be created again.
  A baseline written with another ruleset is accepted with a warning: findings from rules it did
  not run count as new.

## Paths in GitHub Actions

Report paths are relative to the current directory when the scanned directory is inside it,
also when the path to it goes through a symlink, such as macOS's `/tmp`. Otherwise they are
relative to the scanned directory: a path never starts with `..` and is never absolute. When
`GITHUB_WORKSPACE` is set and the scanned directory is inside it, also when one of them is spelled
through a symlink, the `github` and `sarif` formats use paths relative to the workspace instead,
because GitHub resolves annotation and SARIF paths against the repository root. Running the CLI
from `$RUNNER_TEMP` on `"$GITHUB_WORKSPACE"` therefore annotates `.mcp.json`, not
`../../work/repo/repo/.mcp.json`.

`--output` never replaces a file the run read, such as `CLAUDE.md`, the configuration file or a
`.gitignore`, or one that `fix` writes: that exits 2. The file at the path is compared, so another
name for it is refused too: one through a symlinked directory, `/tmp` for `/private/tmp`, or
another letter case where the file system ignores case, as macOS and Windows do by default.
`--output` replaces only a regular file, never through a symlink: a symlink, directory, FIFO or
device at the path exits 2. The one exception is the null device itself: `--output /dev/null`
discards the report, for a run that only needs the exit code. A symlink to `/dev/null` is still
refused.

## Annotations and code scanning

GitHub shows the first 10 error, 10 warning and 10 notice annotations of a step and keeps the
rest in the log. The `github` format therefore writes the annotations that decide the run first:
rules that failed to run, changes that trip `--gate` and policy violations that fail the run.
The findings follow, errors first and `risk` findings first within a severity, then the other
policy violations and notes. When GitHub will not show them all, a notice says how many are only
in the log.

The `stylish` output marks each severity (`✖ error`, `⚠ warning`, `ℹ info`), so ESLint's
problem matcher, which `actions/setup-node` registers in every job, does not read it as ESLint
output and annotate the wrong lines. Use the `github` format for annotations. `actions/setup-node`
registers matchers for tsc and ESLint's compact output too. Where a path or name from the
repository would make a line of text output read as a finding to one of these matchers, such as
a skill directory named `x(1,1): error TS2: Checks passed`, the colon the matcher needs is shown
as `<U+003A>`.

The `sarif` format sets the run's `automationDetails.id` to `agentcheckup/`. GitHub keeps one
analysis per tool and category, and `github/codeql-action/upload-sarif` uses that id instead of
its own `category` input. To upload more than one scan of a repository, such as one per package
of a monorepo, give each scan its own `--sarif-category`:

```sh
npx agentcheckup packages/api --format sarif --sarif-category api --output api.sarif
npx agentcheckup packages/web --format sarif --sarif-category web --output web.sarif
```

The run's id becomes `agentcheckup/<name>/`. A name is letters, digits, `.`, `_` and `-`, in
parts separated by `/`, at most 100 characters. A new category is a separate analysis: GitHub
does not move the alerts of the default category to it. In the
[GitHub Action](https://github.com/mustafakbaser/agentcheckup-action), v0.4.1 or later, the
`sarif-category` input sets this option.

A SARIF rule has one level and, for `risk` rules, one `security-severity`, which GitHub shows
instead of each result's level. Both come from the severity the top-level `rules` of the
configuration sets, else from the rule's default: `error` is 8.0 (High) and `warn` 5.0 (Medium).
A severity from `overrides` applies to the files it matches, so it changes the level of those
results only.

## Exit codes

| Code | Meaning                                                                                                                                                                                                                            |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0    | No findings at or above `--fail-on` (default `error`), the score meets `--min-score`, and no gate tripped. `context` exits 0 unless `--gate` trips.                                                                                |
| 1    | Findings at or above `--fail-on` (only new ones with `--baseline`), a score below `--min-score`, changes caught by `--gate`, or a `--policy` violation that fails the run                                                          |
| 2    | Invalid arguments, configuration, `--cwd` or `--agent`; `--gate` without `--baseline`; a configuration, baseline or policy file that cannot be read or used; an unusable `--output`, or one that would replace a file the run read |
| 3    | Internal error: a rule, a loader or the scanner crashed                                                                                                                                                                            |
| 130  | Interrupted by Ctrl+C (SIGINT) while a command writes (`fix`, `--output`, `skill install`); 143 for SIGTERM, 129 for SIGHUP                                                                                                        |

A score below `--min-score` says so: `Score 95 is below --min-score 96.` follows the score line
in `stylish`, opens the details in `markdown`, and is an error annotation in `github`. The `json`
and `sarif` reports have no place for it, so it goes to stderr.
