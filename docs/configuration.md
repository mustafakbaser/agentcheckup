# Configuration

agentcheckup works without configuration. To change targets or rule severities, add
`agentcheckup.config.json` to the directory you scan.

```json
{
  "$schema": "https://raw.githubusercontent.com/mustafakbaser/agentcheckup/main/schemas/config.schema.json",
  "targets": ["claude-code", "codex", "cursor"],
  "rules": {
    "instr/claude-md-too-long": ["warn", { "maxLines": 300 }],
    "skill/non-portable-field": "off"
  },
  "ignore": ["test/fixtures/**"],
  "overrides": [
    {
      "files": ["examples/**"],
      "rules": { "skill/description-quality": "off" }
    }
  ]
}
```

The configuration is JSON on purpose. agentcheckup never executes code from the repository it
scans, so JavaScript or TypeScript configuration files are not supported.

## Fields

| Field       | Type         | Meaning                                                                                                                                                                                                                                                                                   |
| ----------- | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `targets`   | platform ids | Agents to check against. Rules about other agents are skipped, and `context` plans only their agents. Default: all of `claude-code`, `codex`, `cursor`, `copilot` (its CLI, VS Code and cloud agent), `gemini`, `windsurf` (Devin Desktop), `cline`. The `--targets` flag overrides this. |
| `rules`     | object       | Per rule: `"off"`, `"info"`, `"warn"`, `"error"`, or `[severity, options]`.                                                                                                                                                                                                               |
| `ignore`    | globs        | Files to skip, relative to the scanned directory. Files ignored by `.gitignore` are skipped already. Load plans and the matrix leave them out too, and each plan counts them.                                                                                                             |
| `overrides` | array        | Change rule severities for files matching `files`. Later overrides win. Options can only be set in the top-level `rules`.                                                                                                                                                                 |

Globs use [picomatch](https://github.com/micromatch/picomatch) syntax and match dotfiles.

Unknown rule ids in the configuration produce a warning on stderr. Unknown fields are an error,
so a typo cannot silently disable a check.

## Inline suppressions

Suppress one finding on the next line, with a reason:

```markdown
<!-- agentcheckup-disable-next-line instr/import-unresolved -- generated by our docs build -->

@docs/generated/api.md
```

Suppress rules for a whole file:

```markdown
<!-- agentcheckup-disable-file skill/body-too-long -- reference skill, loaded on demand -->
```

Inside YAML frontmatter, use a YAML comment:

```yaml
---
name: deploy
# agentcheckup-disable-next-line skill/non-portable-field -- Claude Code only
when_to_use: Before every production deploy
---
```

Rules:

- The reason after `--` is required. A directive without one is reported and has no effect.
- A directive that no longer suppresses anything is reported, so stale suppressions do not
  accumulate.
- JSON files cannot hold comments. Use `overrides` for them.
- A directive applies to findings in its own file. That includes a file an instruction file
  imports, such as a `README.md` that `CLAUDE.md` imports with `@README.md`.
- `--untrusted` ignores all inline directives. See
  [Scanning untrusted repositories](#scanning-untrusted-repositories).

## Scanning untrusted repositories

Use `--untrusted` for pull requests from forks and other third-party code. It ignores the
repository's configuration file and all inline directives, so the code under review cannot turn
checks off.

It also does not let the repository's `.gitignore` hide agent configuration. Agents load
committed files whether or not `.gitignore` names them, so a change could otherwise commit a
`.mcp.json` with `git add -f`, list it in `.gitignore` and keep it out of the scan. With
`--untrusted`, agent configuration directories such as `.claude/`, `.cursor/` and `.github/` are
listed, and agent files such as `CLAUDE.md` and `.mcp.json` are read, even where `.gitignore`
excludes them.

### Limitations

These stay hidden with `--untrusted` when `.gitignore` excludes them:

- Directories that are not agent configuration directories, with everything below them. If
  `.gitignore` excludes `packages/`, the scan does not see `packages/x/.claude/settings.json`.
- Files that instruction files import. If `.gitignore` excludes `docs/`, the scan does not read
  `docs/guide.md` for a `CLAUDE.md` that imports `@docs/guide.md`.

To scan everything, add `--no-gitignore`.

## Organization policy

`--policy <file>` checks a scan against rules your organization sets: which MCP servers may run,
forbidden settings, denied tools and commands, required hooks and startup budgets. It implies
`--untrusted`, so the repository cannot switch a check off, and it cannot be combined with
`--config`. A violation fails the run with exit code 1 unless the policy is in audit mode; a
policy file that is not valid exits with code 2. [Organization policy](policy.md) describes the
format, the checks and the trust model.

## How much a scan shows

The `stylish`, `markdown` and `github` formats have three levels of detail. In `stylish`:

| Level   | Flag        | What it shows                                                                                                                                                                                                                                                                                                                 |
| ------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| compact | `--compact` | The findings and the totals, without what each agent misses and without `why`, `fix` and `how` lines. A finding with a fix ends with `fixable` (a safe fix) or `fixable (review)`.                                                                                                                                            |
| default | none        | First, what each agent misses: the skips in the load plans of each agent at the root, each with the class of its fix or `manual`. Under each finding, a `why` line when the plans add a fact the message lacks, then a `fix` line (class and title) or a `how` line (a manual step). Last, the number of fixes of each class. |
| verbose | `--verbose` | The default, plus each rule's docs URL, the first paragraph of its rationale and its sources.                                                                                                                                                                                                                                 |

In `markdown`, the default level adds a table of what each agent misses, a Fix column and a line
on how to preview the fixes. In `github`, it adds `Why`, `Fix` or `How`, and `Docs` lines to each
annotation, whose title names the fix class at every level. `--compact` leaves these additions
out, and `--verbose` shows the same as the default in both formats.

`--compact` and `--verbose` cannot be combined, and they do not change `json`, `sarif` or
`badge`. [Fixing findings](fix.md) explains the fix classes.

## What each agent loads

`agentcheckup context [path]` shows the load plan of each of nine agents, with Copilot's CLI, VS
Code and cloud agent planned separately: what is in context when a session starts, what loads
on demand, the MCP servers and hooks it starts, and what it skips and why. A skip that `agentcheckup fix` can remove ends with `fix: safe`, `fix: review`, or
`needs your words (fix -i)`. It never fails on findings. [What each agent loads](context.md)
explains the output.

| Option                 | Meaning                                                                                                                                                                                                                                                                |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--agent <list>`       | Agents, comma-separated: `claude-code`, `codex`, `cursor`, `copilot-cli`, `copilot-vscode`, `copilot-cloud`, `gemini`, `windsurf` (Devin Local), `cline`. `copilot` stands for its three surfaces, `all` for every agent. Default: those among the configured targets. |
| `--cwd <dir>`          | Plan a session started in this directory, relative to the scanned path. No `..`; the directory must exist. Default: the root.                                                                                                                                          |
| `--matrix`             | Also plan Codex in each directory with an `AGENTS.md`, and show which agent reads which file. Cannot be combined with `--cwd`.                                                                                                                                         |
| `--context-window <n>` | The model's context window in tokens, for limits that depend on it, such as the skills listing.                                                                                                                                                                        |
| `--format <name>`      | `text` (default), `json` or `markdown`. JSON is the same report a scan writes.                                                                                                                                                                                         |

The command also takes `--output`, `--baseline`, `--gate`, `--config`, `--no-config`,
`--untrusted` and `--no-gitignore`, with the same meaning as for a scan. Rule options feed the
plans: the `maxBytes` option of `instr/codex-size-budget` sets the Codex byte limit the plan
assumes, unless a `.codex/config.toml` on the path sets `project_doc_max_bytes`, which wins.
Files that `ignore` matches are left out of the plans and the matrix; each plan says how
many it left out, because agents still load them
([Files the configuration ignores](context.md#files-the-configuration-ignores)). `--untrusted`
does not read the configuration, so it shows them.

On a regular scan, `--context` adds the plans and the matrix that `context --matrix` makes
(every agent at the root, plus Codex in each directory with an `AGENTS.md`) to the report, and
`--context-window` needs it. Use `--context` for the scan that writes a baseline, so a later
comparison also shows how session-start context changed. How findings, inventory items and plan
entries are matched, and exactly when each gate class trips, is in
[Baselines and the gate](context.md#baselines-and-the-gate).

## Baselines and the gate

`--baseline <report.json>` compares a scan with the JSON report of an earlier one, usually the
base branch of a pull request:

```sh
agentcheckup --context --format json --output base.json --fail-on none   # on the base
agentcheckup --baseline base.json --gate security                         # on the change
```

- Findings match by fingerprint and are marked `new` or `unchanged`. `--fail-on` counts new
  findings only; the score still covers every finding. Fingerprints survive lines inserted
  above, re-indentation, trailing commas and reordered JSON keys.
- `--gate` names the security-relevant changes that fail the run: `mcp`, `mcp-unpinned`,
  `permissions`, `hooks`, `env`, `unicode`, `security` for all of them, or `none`. Removals
  never trip it. `--gate` without `--baseline` is a usage error.
- `permissions` trips on every entry that lets an agent do more without asking: any
  `permissions.allow` entry, narrow ones such as `Bash(curl:*)` included, extra directories, a
  skill's `allowed-tools`, MCP auto-approval, Gemini CLI `trust`, a new `defaultMode`, and
  Codex settings such as `approval_policy = "never"`. The
  summary marks broad entries, such as `Bash (broad: runs any shell command)`. `deny` and `ask`
  entries never trip it. [Gate classes](context.md#gate-classes) has every class.
- `--context` on the base scan adds the load plans, so the comparison also shows the change in
  session-start context per agent.
- The baseline is read as untrusted input: at most 64 MiB, a regular file (not a symlink), and
  only a report with a supported `schemaVersion` and the same `fingerprintVersion`. Anything
  else exits with code 2: a baseline written before fingerprint version 2 must be created again.
  A baseline written with another ruleset is accepted with a warning: findings from rules it did
  not run count as new.

## Paths in GitHub Actions

Report paths are relative to the current directory. When `GITHUB_WORKSPACE` is set and the
scanned directory is inside it, the `github` and `sarif` formats use paths relative to the
workspace instead, because GitHub resolves annotation and SARIF paths against the repository
root. Running the CLI from `$RUNNER_TEMP` on `"$GITHUB_WORKSPACE"` therefore annotates
`.mcp.json`, not `../../work/repo/repo/.mcp.json`.

## Exit codes

| Code | Meaning                                                                                                                                               |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0    | No findings at or above `--fail-on` (default `error`), the score meets `--min-score`, and no gate tripped. `context` exits 0 unless `--gate` trips.   |
| 1    | Findings at or above `--fail-on` (only new ones with `--baseline`), a score below `--min-score`, or security-relevant changes caught by `--gate`      |
| 2    | Invalid arguments, configuration, `--cwd` or `--agent`; `--gate` without `--baseline`; a baseline that cannot be read or used; an unusable `--output` |
| 3    | Internal error: a rule, a loader or the scanner crashed                                                                                               |
